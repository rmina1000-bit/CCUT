# CCUT Archive Design — Source Provenance & Project Linking

> 작성: 2026-06-14  
> 갱신: 2026-06-14 (국장 아카이브 신념 명문화 + 제안 그룹핑 + 프로젝트 복기/복원 설계)  
> 배경: 아카이브 UI 설계 논의 + 업계 MAM 시스템 조사 결과 반영

---

## 0. 아카이브 철학 (국장 신념 — 절대 기준)

> 뿌리: `PROJECT_NAVIGATION.md:72` **"모든 산출물은 재사용 가능한 데이터로 저장한다."**

아카이브는 "저장된 파일 목록"이 아니다. **사용자가 자신의 모든 작업을 복기(復棋)할 수 있는 기억 장치**다.

1. **흔적은 사라지지 않는다.** 사용자가 만든 모든 것(원본·제안·편집·내보내기)은 지워도 흔적이 남아야 한다. 삭제는 "숨김"이지 "소멸"이 아니다.
2. **모든 행동은 복기 가능해야 한다.** "아! 내가 이 프로젝트를 어떻게 했지? 맞아 맞아" — 사용자가 자신의 작업 과정을 되짚을 수 있는 기록이 있어야 한다.
3. **삭제한 프로젝트도 되살릴 수 있어야 한다.** "이거 다시 작업해야겠다" 하면 복원해 재작업 가능한 형태로 돌아와야 한다.
4. **모든 것은 프로젝트로 귀속된다.** 제안이 수십 개여도 어느 프로젝트 소속인지 한눈에 보여야 한다. 귀속 없는 산출물은 미아다.
5. **관리는 광범위하다.** 이름 변경만 가능한 것은 관리가 아니다. 조회·복기·복원·이력 추적까지가 관리다.

이 철학은 단순 메타데이터 저장이 아니라 **사용자 작업의 전 생애를 기록·추적·복원하는 시스템**에 대한 선언이다.

## 1. 핵심 원칙

```
원본(Source) = 불변 자산  →  hash identity로 식별
프로젝트(Program) = 원본을 소비하는 컨텍스트
제안(Proposal) = 프로젝트에 종속된 파생물 (1:1)
내보내기(Export) = 프로젝트에 종속된 최종 산출물 (1:1)
```

**원본은 여러 프로젝트에서 재사용 가능하다 (N:M 관계).**  
이 점이 제안/내보내기와 근본적으로 다른 점이며, 별도 설계가 필요한 이유다.

---

## 2. 업계 현황 (2026-06-14 조사)

| 도구 | 해시 기반 | 멀티프로젝트 자산 공유 | 사용 이력 UI |
|---|---|---|---|
| DaVinci Resolve / Premiere Pro / Avid | ❌ 파일경로 | ❌ 프로젝트별 복사 | ❌ 없음 |
| CapCut / Runway | ❌ 클라우드 URL | ❌ 격리 | ❌ 없음 |
| Iconik (기업용 MAM) | ✅ DB 정션 테이블 | ✅ 자산-프로젝트 관계 | △ 감사 로그 수준 |

**결론:** 어떤 상용 NLE도 "이 원본이 N개 프로젝트에서 사용됨"을 UI로 보여주지 않는다.  
CCUT은 DB 구조(ProjectSourceTable)로 이미 이 관계를 갖추고 있으며, UI만 구현하면 된다.

## 3. DB 구조 (현재)

```
SourceTable
  source_id (PK)
  hash_value          ← 파일 fingerprint (이미 존재, UI 미노출)
  title, duration, fps, created_at

ProjectSourceTable    ← N:M 브릿지
  source_id → SourceTable
  program_id → ProgramTable

ProgramTable
  program_id (PK)
  name, status, schema_version
  last_updated_at     ← 마지막 작업 시각

ProposalTable
  proposal_id (PK)
  program_id          ← nullable (레거시 = null)
  source_id

ExportResultTable
  program_id          ← nullable (렌더 시 채워짐)
  program_title       ← 스냅샷 (live JOIN으로 갱신)
```

## 4. 아카이브 탭별 설계 방향

### ① 원본 리스트 (Source List)
- **특징:** 1개 소스 → N개 프로젝트 (N:M)
- **표시:** 파일명 + 단축 해시(8자리) + 사용된 프로젝트 배지(복수)
- **확장 목표:** "사용 이력" 펼침 — 프로젝트별 사용 시각 타임라인
- **미분류:** ProjectSourceTable 연결 없는 소스 → "미분류" 배지

```
[#a2fe8c53] TEST_ASR_0511.mp4
  23분 25초 · 30FPS
  [Arcturus] [Tulip] [Gacrux]   ← 프로젝트 배지
```

### ② 프로젝트 관리 (Program Directory) — "관리"의 재정의

> 국장 지적: "파일 클릭해도 이름 변경 외엔 할 게 없다. 그게 무슨 관리냐."  
> 관리 = 조회 + 복기 + 복원 + 이력 추적.

**카드(접힌 상태):** 프로젝트명 · 상태(DRAFT/삭제됨) · 원본 N개 · 제안 N건 · 내보내기 N회 · 마지막 작업 시각

**카드 클릭 → 상세 드릴다운(펼침):** 한 프로젝트의 전 생애를 한자리에서 복기
```
▼ Tulip                                    [열기/재작업] [이름변경] [삭제]
  ├ 생성:      2026-06-13 05:03
  ├ 마지막작업: 2026-06-14 02:01
  ├ 원본 (58)   ▸ TEST_ASR_0511.mp4, 20211218.mp4 …  (클릭→원본탭)
  ├ 제안 (12)   ▸ A 6건 / B 6건                       (클릭→제안탭 필터)
  └ 내보내기(1) ▸ Tulip.mp4  57.8MB  2026-06-14 01:00 (클릭→재생)
```

**삭제 프로젝트 (soft delete):**
- 삭제는 `status='DELETED'` + `deleted_at` 기록 (행 보존). **hard delete 폐기.**
- 좌측 LeftNav `/projects` 목록에서는 숨김 (작업 공간 깔끔)
- 아카이브 프로젝트 관리 탭에서는 `[삭제됨]` 배지로 표시 → 클릭 시 상세 복기 가능
- **[복원] 버튼:** `status='DRAFT'` 복귀 → LeftNav 재등장, 재작업 가능

### ③ AI 편집제안 이력 (Proposal History) — 프로젝트별 그룹핑

> 국장 지적: "제안서가 어느 프로젝트인지 전혀 알 수 없다. 한 프로젝트에 제안 수십 개일 수 있다. 효율적으로 관리해야 한다. 프로젝트명을 제안명 어딘가에 강력하게 명시하라."

**평면 나열 폐기 → 프로젝트별 그룹 헤더로 묶음:**
```
▼ Tulip  (제안 12건)                              ← 큰 헤더, 강한 색
   → PROP_A_43C083   A Mode · 37초 · 5/25 23:36
   → PROP_B_FC27C4   B Mode · 37초 · 5/25 23:36
   → … (접기/펼치기)
▼ Arcturus  (제안 8건)
   → …
▼ [레거시·미귀속]  (제안 228건)                   ← 역추적 실패분 격리
```
- 그룹 정렬: 최근 제안 순
- 각 그룹 접기/펼치기 (수십 개 대응)
- program_id 직접 연결 / source 역추적(≈) / 레거시 3단계는 그룹 헤더 색으로 구분
- 제안명(PROP_*)은 내부 ID라 보조 정보로 격하, **프로젝트명이 1차 식별자**

### ④ 내보낸 영상 (Exports)
- **현행 유지:** program_title live JOIN으로 최신 프로젝트명 표시 ✅

## 6. 미래 확장 아이디어 (CCUT v2+)

- **Content-Addressable Archive:** 소스를 hash 기반으로 저장, 동일 파일 인제스트 시 자동 중복 감지
- **Clip-Level Lineage:** ProposalTable.sequence JSON에서 어느 fragment_id가 어느 구간을 썼는지 역추적
- **Source Card 사용 타임라인:** Gantt 스타일로 각 프로젝트의 사용 시점 시각화
- **C2PA 호환:** 영상 출처 메타데이터 표준(Coalition for Content Provenance and Authenticity) 대응

## 7. 업계 심층 조사 종합 (2026-06-14) — 방송국·데이터센터·전문 아카이브

### 7.1 방송국 MAM 4계층 자산 모델 (BBC/NHK/PBS 공통)

방송국은 자산을 **4계층**으로 분리한다. CCUT 구조와 1:1 대응한다:

| 방송국 계층 | 정의 | CCUT 대응 |
|---|---|---|
| **RAW (원본)** | 카메라 원본. 불가침, 영구 보존 | **Source** (원본 영상) |
| **Proxy** | 저해상 브라우징/편집용 사본 | proxy/thumbnail (이미 생성) |
| **WIP / Rough cut** | 작업 중 편집본·제안 | **Proposal** (A/B 제안) |
| **Master (완성본)** | 승인된 최종 송출본 | **Export** (내보낸 영상) |

핵심 규율: **RAW와 완성본은 절대 섞지 않는다.** RAW는 영구, proxy/WIP는 짧은 보존, master는 영구.

### 7.2 OAIS 참조 모델 (ISO 14721) — 모든 아카이브의 표준 골격

```
SIP (입수) → AIP (보존, 불변 정본) → DIP (제공, 사용자 맞춤본)
```
- **원칙:** 사용자가 보는 형태(DIP)와 보존 정본(AIP)을 분리. 정본은 영구 불변.
- CCUT 적용: 원본(AIP) 불변 + 화면 표시용(DIP)은 별도. 이미 hash로 정본 보장.

### 7.3 PREMIS 이벤트 로그 — "복기"의 핵심 인프라 ★

> 국장 신념 "모든 행동을 복기"의 업계 정답이 바로 이것.

PREMIS는 모든 아카이브 객체에 대해 **Object · Event · Agent · Rights** 4요소를 기록한다.
- **Event:** 생성·수정·이동·접근·삭제 등 모든 행동을 `누가(Agent) · 무엇을 · 언제(timestamp) · 왜`로 기록
- **불변·추가 전용(append-only):** 로그는 고치지 않고 쌓기만 함 → 위조 불가 감사 추적(WORM)

**→ CCUT 신규 제안: `ProjectEventTable` (이벤트 로그 테이블)**
프로젝트 생성/이름변경/원본추가/제안생성/내보내기/삭제/복원을 모두 한 줄씩 기록.
이것이 "아! 내가 이 프로젝트를 어떻게 했지" 복기 화면의 데이터 원천이 된다.

### 7.4 Fixity (무결성) — 해시는 디지털 봉인

아카이브는 입수 시 해시(MD5/SHA)를 만들고 주기적으로 대조해 파일 불변을 증명한다.
- CCUT: `SourceTable.hash_value` 이미 보유 → #8자리 UI 노출 완료. "정본 보증서" 역할.

### 7.5 자산 ≠ 조직 구조 (Iconik/Dalet 핵심 통찰) ★

전문 MAM의 가장 중요한 설계: **자산 저장과 조직 구조를 분리.**
- 같은 원본이 여러 컬렉션/프로젝트에 **중복 저장 없이** 동시에 등장
- CCUT: `ProjectSourceTable`(N:M 브릿지)로 이미 정확히 이 구조 ✅

### 7.6 Soft Delete + 휴지통 (전 업계 공통)

| 시스템 | 보존 정책 |
|---|---|
| Apple Photos | 30일 "최근 삭제" 후 영구 삭제 |
| Iconik | 24시간 휴지통(설정 가능) |
| 방송국 | 7~90일 복구 창 후 hard-delete |
| Dalet | 삭제 플래그만(행 보존), 수동 purge |

→ CCUT: 현행 hard-delete 폐기 → soft-delete(`status='DELETED'`) + 휴지통/복원.

## 8. CCUT 적용 제안 — "방송국급 내부, Google Photos급 표면"

### 설계 철학
> **사용자는 아무 생각 없이 단순하게. 내부는 방송국 표준으로 강력하게.**
> 업계 UX 원칙: Progressive Disclosure(점진적 노출) + 자동 조직화(invisible) + 안전한 복구(soft-delete).

### 표면(사용자가 보는 것) — 단순 4탭, 생각 0
- **카드 그리드**: Google Photos처럼 썸네일+제목+2줄. 복잡한 메타데이터는 숨김.
- **클릭하면 펼쳐짐**: 카드 → 드릴다운 상세 (progressive disclosure). 평소엔 안 보임.
- **자동 정리**: 사용자는 폴더를 만들지 않는다. 시스템이 프로젝트별·날짜별·원본별로 자동 그룹.
- **휴지통**: "삭제한 항목은 N일간 보관" + 원터치 복원. 삭제 불안 제거.

### 내부(보이지 않는 강력함) — 방송국 표준
| 업계 표준 | CCUT 구현 | 상태 |
|---|---|---|
| 4계층 자산 분리 | Source / Proposal / Export 탭 분리 | ✅ |
| Fixity(해시 봉인) | hash_value #8자리 | ✅ |
| 자산≠조직(N:M) | ProjectSourceTable | ✅ |
| OAIS 정본 불변 | 원본 불가침 | ✅ |
| **PREMIS 이벤트 로그** | **ProjectEventTable (신규)** | 🔴 제안 |
| **Soft-delete + 휴지통** | status='DELETED'+복원 | 🔴 제안 |
| 프로젝트 활동 복기 | 드릴다운 타임라인 | 🔴 제안 |

### 사용자 시나리오로 본 결과물
- "이 영상 어디 썼더라?" → 원본 카드 "사용 이력" 펼침 (✅ 완료)
- "이 제안 뭐였지?" → 제안이 프로젝트별로 묶여 한눈에 (🔴 제안)
- "내가 이 프로젝트 어떻게 했지?" → 프로젝트 클릭 → **활동 타임라인**(생성→원본추가→제안 12건→내보내기→삭제) 복기 (🔴 제안)
- "아 이거 다시 해야지" → 휴지통에서 **복원** → 재작업 (🔴 제안)

### 한 줄 결론
CCUT 아카이브 = **OAIS 골격 + PREMIS 이벤트 로그 + 방송국 4계층 + Iconik N:M**을, **Google Photos의 단순함**으로 감싼다. 백엔드는 방송국, 표면은 사진첩.
